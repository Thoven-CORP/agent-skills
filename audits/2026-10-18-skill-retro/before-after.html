What the WARN row caught on its first real run

The new backend engine's own receipt run reported WARN on two surviving hunks in lib/thoven/verify.rb: two @mapped_specs = {} resets that no spec noticed. One was dead code and was deleted. The other now has a spec that fails if the line is removed. The old engine would have reported this as BLOCKED and the run would have been waived in prose. The WARN row names the hunks and lets the run finish.

Why each change works

Selecting rows by path. A check can only find a defect in code it reads. Brakeman reads controllers, bundler-audit reads the Gemfile, the OpenAPI diff reads routes and serializers. A service method touches none of those, so running them is 262 s that cannot fail. Picking rows by the paths in the diff drops the checks that have nothing to read.

Direct importers, once. vitest related follows the import graph outward with no limit, so one shared component pulls in every screen that renders it and every test of those screens. Nine files, 27 s, for two buttons. A bug in the component shows up in the component's own test or in the test of something that imports it directly. Two hops away you are mostly re-running the same assertions on a bigger page.

Mutation only where it pays. Mutation testing reverses a hunk and asks whether a test notices. That is worth the reruns when the hunk is logic with a mapped test: a service, a hook, a store. On a component, reversing a JSX hunk mostly removes a button, and the test that would notice is the one already in the related row. So the component case ran 68 s of reruns to learn what the 2 s test had already said. Scoping mutation to lib, hooks, contexts, store and models keeps the reruns where a silent logic change can hide.

Mutation against the one mapped spec. The backend reran every selected spec per hunk. The spec mapped to the changed file is the one whose assertions can notice that file's hunk; the others boot Rails and assert about other code. One spec per hunk is the same signal at a quarter of the time (92 s to 22 s).

WARN instead of BLOCK. BLOCKED stops the run and leaves no receipt, so the only way forward was a sentence in chat and a `--no-verify` push. WARN finishes the run, writes the receipt, and names the surviving hunks. The first real backend run showed why: two dead resets nobody asserted on, listed by hunk, one deleted and one covered within the hour. The old engine would have stopped at the first and been waived.

The design-scans row. The 19 scan suites open files with fs and read them as text, so they import nothing from components/. Vitest's import graph therefore never links them to a component change, and the related row never ran them. Selecting them by path, not by import, is the whole fix. They run in 7 s and they are the check for the defect class you flag most.

Docs-only diffs. A diff of only markdown has no test to run. The old frontend engine ended with "No test files found" and the old backend engine refused a plan with no rows. One git diff --check row gives the run something true to say, and the empty-diff refusal stays, because an empty diff is a sign the caller is in the wrong tree.

bin/verify out of pre-push. A push happens many times per slice and pre-push diffs against origin/main, which on an integration branch is the whole branch. That is why pushes took 7 to 20 minutes and 130 of them went --no-verify. Verification belongs once per slice, before DONE, against the integration branch, where the diff is the slice. CI on the integration PR is the full run.
