# Weekly Ops Report

A Monday call sheet. Two questions:

1. **Who do I watch this week?** — people with lessons coming up
2. **Who do I call about last week?** — people who did something

Names are the product. Counts are context.

The numbers come from tested Ruby. Your value is the layer it can't do: noticing
what changed since last Monday, and checking the things a static report only
implies.

## Lead with the person, not the plumbing

Andres reads the first two lines and acts. Everything before the first name is
tax he pays to reach the point.

So open with the most consequential human fact you found. The file path, the
caveats, and the methodology go at the bottom — he can scroll if he wants them,
and usually he won't.

**Good:**

> **Audrey Mora is now 53 days waiting on Maycee Harrison** — up from 46 last
> Monday, four credits still locked. This is the one to call today.
>
> Javanna's two Thursday requests both got answered this week; last week only
> one did. Active fell again, 27 → 22, fourth straight week, still parents and
> students rather than teachers.
>
> Two new names in Confirmed — Caden Adams with Marcus Gonzalez, and Giada
> Warford, who was on the nudge list last week.
>
> Nothing else moved. Full report: `docs/analytics/product-team/WEEKLY_REPORT_2026-08-10.md`

**Bad** — this is the same content, and it fails, because the thing that matters
is now in paragraph three:

> Report written to `docs/analytics/product-team/WEEKLY_REPORT_2026-08-10.md`.
>
> One caveat before the numbers: the prior report was generated by a different
> script, so the formats aren't directly comparable…
>
> **Audrey Mora is now 53 days waiting.**

If a week is genuinely quiet, say so in one line. "Nothing moved except X" is a
useful sentence, and it makes the weeks you *do* flag more credible.

## Running it

From the backend repo root:

```bash
set -a && source .env && set +a && DATABASE_URL="$PROD_DATABASE_URL" \
  bundle exec rails runner scripts/weekly_ops_report.rb \
  --output docs/analytics/product-team/WEEKLY_REPORT_$(date +%F).md
```

Read-only against production. Never write, and never `REFRESH MATERIALIZED VIEW`
to improve a number — a stale figure labelled stale beats a fresh one nobody can
trust.

If the script fails, say so rather than reconstructing its output by hand.

## Don't re-derive the report. Do verify a specific claim.

These sound contradictory and aren't, so here's the line between them.

**The report's own figures always come from the script.** `Analytics::WeeklyOpsReportQuery`
exists because four production metrics were each measuring something different
from what their label said — pending requests counted as "booked", Teach Mode
counted before anyone joined. A second query path drifts from the tested one and
you get two tools disagreeing about the same week. That is the disease. Don't
reintroduce it.

**A targeted read-only query to answer a question the report doesn't answer is
not that, and is often the better answer.** The report is a snapshot. When
Andres asks whether something *actually happened*, absence from a snapshot is
weak evidence — a name can drop off the nudge list because they booked, because
their request is still pending, or because their wallet hit zero. Those mean
completely different things and he cares which.

So when the question contains "actually", "really", "did they", or otherwise
asks you to confirm rather than summarise: go look. Query production read-only
for that specific parent, teacher, or slot. Then say what you found and how you
found it.

> Nobody from the nudge list booked. I checked each of the five directly rather
> than inferring from the report: Giada Warford now has a request in for Thu, but
> it's still pending Marissa's approval — not a booking. The other four have had
> no booking activity at all since Jul 27.

That is a materially better answer than "none of them appear in this week's
confirmed table", and it takes one query.

## Comparing to last week

```bash
ls -1 docs/analytics/product-team/WEEKLY_REPORT_*.md | tail -3
```

Reports before 2026-08-03 came from an older script with a different structure.
They still contain useful facts — who was stuck, who had credits — but the
sections don't line up, so read them for content rather than diffing them
mechanically. Say when you've done that, briefly, at the bottom.

**Do both halves of a "since last week" question.** Going to production for the
current truth is the right instinct, but it answers only half — "what is true
now". The other half is "what was true then", and that lives in the previous
report. Skipping it silently drops the comparison the question actually asked
for, and Andres has no way to tell you skipped it.

So: read the prior report, say plainly if its format doesn't line up, and give
him the comparison you can honestly make from it. "Shelby and Amanda were both
flagged stuck on Jul 27 and both still are" is a real week-over-week answer even
when the two files have nothing structurally in common.

Worth calling out, roughly by weight:

- Someone new in the alert block, or an existing alert getting older. 46 days
  becoming 53 is not "still waiting" — it's deteriorating on a schedule.
- A pending request answered, or still not answered. Teachers who don't respond
  are a supply problem wearing a scheduling costume.
- A nudge-list parent who booked, or who crossed the 14-day quiet line.
- Direction on Active. One week is noise; four in the same direction is the most
  important thing on the page.
- Any first-time name in Confirmed.

Skip what didn't change.

## Reading the report honestly

Mention these when they're load-bearing for a claim you're making — not as
boilerplate every week.

- **The Active row counts a different population** than Sessions and Purchases
  below it: it reads the WAU matview, which includes test and internal accounts.
  Directionally useful, not magnitude-comparable. The report footnotes this.
- **Two known-test accounts are still unflagged in production** —
  `keriparent@icloud.com`, `musicwithkeri@gmail.com`. They appear until Andres
  approves a data change.
- **Keri Erten (`keri@thoven.co`) is excluded from this report only.** She's the
  cofounder and a real teacher; every other analytics surface counts her. This is
  usually why this report and the admin panel disagree.
- **`credits_reserved` is maintained on very few wallets.** Never reason about
  booked-ness from it; the report already derives that from real slots.

## When the question is bigger than the report

If Andres asks something broad — "what should I be worried about", "how are we
doing" — the report is *one* input, not the boundary of the answer. A stranded
parent matters; so does a framework going end-of-life this week, a red CI job, or
an open P1. Check `TECH_DEBT.md` and recent `docs/audits/` alongside the report,
and lead with whatever is genuinely most urgent even when it has nothing to do
with lessons.

Answering a broad question with only what this report happens to cover is a way
of being confidently incomplete.

## Not for

- **Platform trends and funnels** — admin Feature Analytics, `https://thoven.co/admin`.
- **Fixing what it surfaces.** Refunds and production data changes are Andres's
  call and need his explicit approval.
- **Ad-hoc analytics** the report doesn't cover — the query catalogue is
  `docs/analytics/WEEKLY_ANALYTICS_QUERIES.md`.
